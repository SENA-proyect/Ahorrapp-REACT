## 2. Requerimiento verificado

Texto del documento de requisitos (las precondiciones se muestran en una sola línea):

> **RF-24: Exportación nativa de reportes financieros (PDF).** El sistema deberá permitir generar en el dispositivo un reporte en PDF para un rango de fechas y un período de presupuesto seleccionados, con las secciones: portada y resumen, distribución de gastos e ingresos, ahorros, deudas, fondo de emergencia, presupuesto y evolución. Al terminar, se abre la hoja de compartir nativa del sistema operativo.
>
> **Precondiciones:** El usuario tiene una sesión activa y conexión a internet; Cuenta con registros financieros almacenados.
>
> **Requisitos específicos:**
> - **RF-24.1:** El PDF se genera en el dispositivo.
> - **RF-24.2:** El reporte corresponde a un rango de fechas y a un período de presupuesto seleccionados.
> - **RF-24.3:** El reporte incluye: portada y resumen, distribución de gastos e ingresos, ahorros, deudas, fondo de emergencia, presupuesto y evolución.
> - **RF-24.4:** Al terminar, se abre la hoja de compartir nativa del sistema operativo.
> - **RF-24.5:** Las secciones sin datos se indican como no disponibles.
> - **RF-24.6:** El reporte no incluye datos que el backend no devuelva.
> - **RF-24.7:** La generación requiere conexión a internet.

## 3. Entorno y estrategia

| Elemento | Detalle |
|---|---|
| Pruebas de backend | Jest (`^30.5.2`) + Supertest (`^7.3.2`); configuración en `Backend/jest.config.js` y `test/backend/setupEnv.js` |
| Pruebas de frontend | Vitest (`^5.1.0`) + Testing Library (`react`, `user-event`, `jest-dom`) + jsdom; configuración en `Frontend/vite.config.js` (bloque `test`) y `Frontend/setupTests.js` |
| Comando backend | `npx jest rf24` (desde `Backend/`) |
| Comando frontend | `npx vitest run test/frontend/rf24` (desde `Frontend/`; `npm test` abre el modo observador) |

**Estrategia backend.** Se monta una aplicación Express con solo las rutas del módulo. La base de datos y los servicios dependientes están **simulados (mocks)**, por lo que no se accede a Supabase ni a Firebase. El token JWT se firma realmente, de modo que `verifyToken` se ejecuta sin simulación.

**Estrategia frontend.** Cada página se renderiza completa con Testing Library; `fetch` se reemplaza por un simulador (`test/frontend/helpers/fetchMock.js`) que responde por método y URL y registra las llamadas (URL, cabecera `Authorization` y cuerpo). El encabezado de navegación y los contextos de avisos se sustituyen por dobles. Se simula el teclado y los clics del usuario (`user-event`).

## 7. Observaciones y limitaciones

1. **Móvil no cubierto.** RF-24 describe una función nativa del dispositivo (hoja de compartir, RF-24.4). El proyecto entregado contiene solo backend y web, por lo que se probó el generador web (`generarreportepdf.js`) y los datos del backend.
2. **Leyenda «no disponible» (RF-24.5).** En la web, las secciones 2–5 (ingresos, gastos, ahorros, deudas) sin datos quedan con título y subtítulo pero sin leyenda; solo «Imprevistos» muestra «No se registraron imprevistos durante el período.». El RF-11.6 admite omitir secciones, pero RF-24.5 pide indicarlas como no disponibles. Queda fijado en la prueba «OBSERVACIÓN».
3. **Página en blanco sin presupuesto.** Cuando no se elige un período de presupuesto, la sección 8 se omite pero igualmente se agrega su página, que queda vacía (solo el pie «Página 8»). El PDF resultante tiene 9 páginas con 8 secciones. Queda fijado en una prueba «OBSERVACIÓN».
4. **«Ingresos por fuente» no se imprime.** El informe consulta ingresos por fuente (RF-11), pero `generarIngresos` solo dibuja la tabla «por categoría». Queda fijado en una prueba «OBSERVACIÓN».
5. **jsPDF simulado.** El PDF no se renderiza: se registran los textos, las páginas y el nombre del archivo. No se valida el aspecto visual (colores, gráficas, diseño).
6. **Pruebas con BD y red simuladas.** Se verifica la lógica del controlador, los parámetros enviados a la base de datos y el comportamiento de las pantallas, pero no se ejecutan consultas reales ni se prueba contra PostgreSQL/Supabase; restricciones como los `CHECK` o el aislamiento por usuario a nivel SQL no se validan contra la base real.
7. **Precondición «cuenta activa».** En el código revisado solo se valida el token JWT; no se comprueba que la cuenta esté activa. No hay prueba asociada (se revisará junto con RF-09).
8. **Alcance.** Se cubren backend y frontend web. La aplicación móvil no forma parte del proyecto entregado y no se probó.
