## 2. Requerimiento verificado

Texto del documento de requisitos (las precondiciones se muestran en una sola línea):

> **RF-03: Gestionar gastos.** El sistema deberá permitir registrar, consultar, editar, eliminar y clasificar gastos por categoría, fecha y monto, y asociarlos opcionalmente a un dependiente económico, manteniendo un listado organizado para el control y análisis de la información financiera personal.
>
> **Precondiciones:** El usuario ha iniciado sesión; La cuenta está activa.
>
> **Requisitos específicos:**
> - **RF-03.1:** El monto debe ser mayor que cero (CHECK (`monto > 0`)).
> - **RF-03.2 (web):** El formulario exige un monto mínimo de 50.
> - **RF-03.3:** La categoría seleccionada debe existir (clave foránea a `categorias`); en el backend su selección es opcional.
> - **RF-03.4:** El gasto puede asociarse a un dependiente económico (RF-10).
> - **RF-03.5:** Cada usuario accede solo a sus propios gastos.

## 3. Entorno y estrategia

| Elemento | Detalle |
|---|---|
| Pruebas de backend | Jest (`^30.5.2`) + Supertest (`^7.3.2`); configuración en `Backend/jest.config.js` y `test/backend/setupEnv.js` |
| Pruebas de frontend | Vitest (`^5.1.0`) + Testing Library (`react`, `user-event`, `jest-dom`) + jsdom; configuración en `Frontend/vite.config.js` (bloque `test`) y `Frontend/setupTests.js` |
| Comando backend | `npx jest rf03` (desde `Backend/`) |
| Comando frontend | `npx vitest run test/frontend/rf03` (desde `Frontend/`; `npm test` abre el modo observador) |

**Estrategia backend.** Se monta una aplicación Express con solo las rutas del módulo. La base de datos y los servicios dependientes están **simulados (mocks)**, por lo que no se accede a Supabase ni a Firebase. El token JWT se firma realmente, de modo que `verifyToken` se ejecuta sin simulación.

**Estrategia frontend.** Cada página se renderiza completa con Testing Library; `fetch` se reemplaza por un simulador (`test/frontend/helpers/fetchMock.js`) que responde por método y URL y registra las llamadas (URL, cabecera `Authorization` y cuerpo). El encabezado de navegación y los contextos de avisos se sustituyen por dobles. Se simula el teclado y los clics del usuario (`user-event`).

## 7. Observaciones y limitaciones

1. **Mínimo de 50 solo en la web (RF-03.2).** El backend acepta cualquier monto mayor que cero; una llamada directa a la API con un gasto de 10 se guarda (prueba «el mínimo de 50 NO se exige en el backend»). Si la regla debe ser global, habría que moverla al backend.
2. **Fecha futura.** El formulario web rechaza fechas futuras en gastos; esa regla no figura en el RF-03 y, según el código revisado, el backend solo valida el formato de la fecha.
3. **Pruebas con BD y red simuladas.** Se verifica la lógica del controlador, los parámetros enviados a la base de datos y el comportamiento de las pantallas, pero no se ejecutan consultas reales ni se prueba contra PostgreSQL/Supabase; restricciones como los `CHECK` o el aislamiento por usuario a nivel SQL no se validan contra la base real.
4. **Precondición «cuenta activa».** En el código revisado solo se valida el token JWT; no se comprueba que la cuenta esté activa. No hay prueba asociada (se revisará junto con RF-09).
5. **Alcance.** Se cubren backend y frontend web. La aplicación móvil no forma parte del proyecto entregado y no se probó.
6. **Requisito para ejecutar las pruebas.** Estas pruebas cargan `movimientosController.js`, que en la copia recibida exporta `getMovimientos` sin definirla (ver `README.md` de esta carpeta, hallazgo H-01). Mientras no se corrija, las pruebas de backend de este módulo no pueden cargar el controlador.
