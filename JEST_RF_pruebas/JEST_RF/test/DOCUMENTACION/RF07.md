## 2. Requerimiento verificado

Texto del documento de requisitos (las precondiciones se muestran en una sola línea):

> **RF-07: Gestionar deudas.** El sistema deberá permitir registrar, consultar, modificar y eliminar deudas con una persona o entidad (fuente), definiendo monto total, número de cuotas, fechas y categoría, y registrar el pago de cuotas. Cada pago calcula su valor proporcional (monto ÷ cuotas totales × cuotas pagadas) y la deuda pasa a estado “pagada” al completar sus cuotas.
>
> **Precondiciones:** El usuario ha iniciado sesión; La cuenta está activa.
>
> **Requisitos específicos:**
> - **RF-07.1:** La fuente de la deuda es obligatoria.
> - **RF-07.2:** El monto debe ser mayor que cero.
> - **RF-07.3:** El número de cuotas debe ser mayor que cero.
> - **RF-07.4:** Las cuotas pagadas no pueden exceder el total de cuotas.
> - **RF-07.5:** Cada pago debe ser de al menos una cuota.
> - **RF-07.6:** No se admiten pagos en deudas ya pagadas.
> - **RF-07.7:** La fecha de fin no puede ser anterior a la fecha de inicio.
> - **RF-07.8:** El valor de cada pago se calcula como monto ÷ cuotas totales × cuotas pagadas.
> - **RF-07.9:** La deuda pasa a estado “pagada” al completar sus cuotas.
> - **RF-07.10 (web):** La eliminación requiere confirmación explícita del usuario.
> - **RF-07.11:** Las deudas con vencimiento próximo generan una notificación (RF-13).

## 3. Entorno y estrategia

| Elemento | Detalle |
|---|---|
| Pruebas de backend | Jest (`^30.5.2`) + Supertest (`^7.3.2`); configuración en `Backend/jest.config.js` y `test/backend/setupEnv.js` |
| Pruebas de frontend | Vitest (`^5.1.0`) + Testing Library (`react`, `user-event`, `jest-dom`) + jsdom; configuración en `Frontend/vite.config.js` (bloque `test`) y `Frontend/setupTests.js` |
| Comando backend | `npx jest rf07` (desde `Backend/`) |
| Comando frontend | `npx vitest run test/frontend/rf07` (desde `Frontend/`; `npm test` abre el modo observador) |

**Estrategia backend.** Se monta una aplicación Express con solo las rutas del módulo. La base de datos y los servicios dependientes están **simulados (mocks)**, por lo que no se accede a Supabase ni a Firebase. El token JWT se firma realmente, de modo que `verifyToken` se ejecuta sin simulación.

**Estrategia frontend.** Cada página se renderiza completa con Testing Library; `fetch` se reemplaza por un simulador (`test/frontend/helpers/fetchMock.js`) que responde por método y URL y registra las llamadas (URL, cabecera `Authorization` y cuerpo). El encabezado de navegación y los contextos de avisos se sustituyen por dobles. Se simula el teclado y los clics del usuario (`user-event`).

## 7. Observaciones y limitaciones

1. **Número de cuotas «obligatorio» (RF-07 / Datos almacenados).** El RF indica que las cuotas son obligatorias y mayores que cero, pero backend y web aceptan dejarlas vacías (se guarda `null` y la deuda se trata como «Pago único»). Las pruebas fijan este comportamiento («pago único») y rechazan solo valores inválidos (0, negativos, decimales, texto). Conviene decidir si se ajusta el RF o la validación.
2. **Rechazos del backend en la web.** `abonarDeuda` lanza una excepción ante respuestas no exitosas y la pantalla muestra «Error al conectar con el servidor» en vez del motivo (p. ej. 409 «Esta deuda ya está pagada»). Queda fijado en la prueba «OBSERVACIÓN».
3. **Tarea programada.** `DeudasJob` se prueba capturando la función registrada en `node-cron` y ejecutándola; no se espera a las 06:00 reales.
4. **Marcas de vencimiento.** «Vencida» / «Vence en Nd» se calculan en la web con la fecha del sistema; la prueba de «vence pronto» usa una fecha relativa a hoy.
5. **Pruebas con BD y red simuladas.** Se verifica la lógica del controlador, los parámetros enviados a la base de datos y el comportamiento de las pantallas, pero no se ejecutan consultas reales ni se prueba contra PostgreSQL/Supabase; restricciones como los `CHECK` o el aislamiento por usuario a nivel SQL no se validan contra la base real.
6. **Precondición «cuenta activa».** En el código revisado solo se valida el token JWT; no se comprueba que la cuenta esté activa. No hay prueba asociada (se revisará junto con RF-09).
7. **Alcance.** Se cubren backend y frontend web. La aplicación móvil no forma parte del proyecto entregado y no se probó.
8. **Requisito para ejecutar las pruebas.** Estas pruebas cargan `movimientosController.js`, que en la copia recibida exporta `getMovimientos` sin definirla (ver `README.md` de esta carpeta, hallazgo H-01). Mientras no se corrija, las pruebas de backend de este módulo no pueden cargar el controlador.
