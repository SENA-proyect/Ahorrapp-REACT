## 2. Requerimiento verificado

Texto original (documento IEEE, sin modificaciones):

> **RF-02: Gestionar ingresos.** El sistema deberá permitir a los usuarios registrar, consultar, editar, eliminar y clasificar ingresos (salarios, comisiones, bonificaciones y otras fuentes) indicando monto, fuente, descripción, fecha y categoría, manteniendo un listado organizado disponible para análisis financiero.
>
> **Precondiciones:** el usuario debe haber iniciado sesión; la cuenta debe estar activa.
>
> **Restricciones:** el monto debe ser mayor que cero (`CHECK (monto > 0)` en base de datos; el backend además rechaza montos vacíos). Cada usuario solo accede a sus propios ingresos. La fecha de registro es opcional; si no se envía, se usa la fecha actual.

## 3. Entorno y estrategia

| Elemento | Detalle |
|---|---|
| Framework de pruebas | Jest (versión declarada en `package.json`: `^30.5.2`) |
| Pruebas HTTP | Supertest (`^7.3.2`) |
| Archivo de pruebas | `test/backend/rf02/ingresos.test.js` |
| Configuración | `Backend/jest.config.js` y `test/backend/setupEnv.js` |
| Comando | `npx jest ingresos` (desde la carpeta `Backend`) |

**Estrategia.** Las pruebas montan una aplicación Express con solo las rutas de movimientos. La base de datos y los servicios dependientes (`actualizarIngresoReal`, notificaciones, operaciones móviles, sincronización) están **simulados (mocks)**, por lo que no se accede a Supabase. El token JWT se firma realmente, de modo que el middleware de autenticación se ejecuta sin simulación.

**Entorno frontend.** Vitest (`^5.1.0`) + Testing Library (`react`, `user-event`, `jest-dom`) + jsdom. Configuración en `Frontend/vite.config.js` (bloque `test`) y `Frontend/setupTests.js`. Comando: `npx vitest run test/frontend/rf02` (desde `Frontend/`).

**Estrategia frontend.** La página se renderiza completa; `fetch` se reemplaza por un simulador (`test/frontend/helpers/fetchMock.js`) que responde por método y URL y registra URL, cabecera `Authorization` y cuerpo. El encabezado y los contextos de avisos se sustituyen por dobles. Las pruebas comunes de las pantallas CRUD están en `test/frontend/helpers/crudModulo.jsx` (compartidas con RF-05).

## 7. Observaciones y limitaciones

1. **Pruebas con BD simulada.** Se verifica la lógica del controlador y los parámetros enviados a la base de datos, pero no se ejecutan consultas reales. La restricción `CHECK (monto > 0)` y el aislamiento de datos a nivel SQL no se validan contra PostgreSQL; para ello haría falta una prueba de integración con una BD de pruebas.
2. **Precondición "cuenta activa".** En el código revisado (`verifyToken` y el controlador) solo se valida el token JWT; no se comprueba que la cuenta esté activa. No hay prueba asociada. Se revisará junto con RF-09 (Iniciar sesión).
3. **Edición no parcial.** `PUT` guarda `null` en descripción, fuente y categoría si no se envían (solo la fecha conserva su valor anterior). Es el comportamiento actual y queda fijado en CP-ING-36.
4. **Categoría.** El backend delega en la clave foránea la existencia de la categoría (CP-ING-28). En el código revisado no se valida que la categoría pertenezca al usuario.
5. **Alcance.** Se cubren backend y frontend web. La aplicación móvil no forma parte del proyecto entregado y no se probó; el manual de usuario de RF-02 se documentará aparte.
6. **Requisito para ejecutar las pruebas de backend.** En la copia recibida, `movimientosController.js` exporta `getMovimientos` sin definirla; el controlador no carga y esta suite falla hasta corregirlo (ver `README.md`, hallazgo H-01). Con la corrección, las 59 pruebas pasan.
7. **Fecha futura (web).** El formulario rechaza fechas futuras en ingresos; esa regla no figura en el RF-02 y, según el código revisado, el backend solo valida el formato de la fecha.
8. **Pruebas del frontend con red simulada.** Se verifican la interacción, las validaciones y las llamadas HTTP (URL, token y cuerpo), pero no contra el backend real.
