## 2. Requerimiento verificado

Texto del documento de requisitos (las precondiciones se muestran en una sola línea):

> **RF-26: Gestionar presupuestos y períodos presupuestales.** El sistema deberá permitir crear, consultar, editar, eliminar y activar perfiles de presupuesto, definiendo el día de corte y el porcentaje asignado a gastos, deudas, imprevistos, ahorros y fondo de emergencia. Con un perfil activo, el usuario podrá abrir y cerrar períodos presupuestales, consultar el período activo y el histórico (paginado), y ajustar o actualizar el ingreso estimado y real del período. Cada período calcula los montos por módulo.
>
> **Precondiciones:** El usuario ha iniciado sesión.
>
> **Requisitos específicos:**
> - **RF-26.1:** Los cinco porcentajes del perfil (gastos, deudas, imprevistos, ahorros y fondo de emergencia) deben sumar exactamente 100 %.
> - **RF-26.2:** Cada porcentaje debe estar entre 0 y 100.
> - **RF-26.3:** Solo puede haber un perfil de presupuesto activo por usuario.
> - **RF-26.4:** El día de corte debe estar entre 1 y 31.
> - **RF-26.5:** La fecha de fin de un período debe ser posterior a la de inicio.
> - **RF-26.6:** Los períodos solo pueden abrirse con un perfil activo.
> - **RF-26.7:** Cada período calcula los montos asignados a cada módulo.
> - **RF-26.8:** El histórico de períodos se consulta de forma paginada.

## 3. Entorno y estrategia

| Elemento | Detalle |
|---|---|
| Pruebas de backend | Jest (`^30.5.2`) + Supertest (`^7.3.2`); configuración en `Backend/jest.config.js` y `test/backend/setupEnv.js` |
| Pruebas de frontend | Vitest (`^5.1.0`) + Testing Library (`react`, `user-event`, `jest-dom`) + jsdom; configuración en `Frontend/vite.config.js` (bloque `test`) y `Frontend/setupTests.js` |
| Comando backend | `npx jest rf26` (desde `Backend/`) |
| Comando frontend | `npx vitest run test/frontend/rf26` (desde `Frontend/`; `npm test` abre el modo observador) |

**Estrategia backend.** Se monta una aplicación Express con solo las rutas del módulo. La base de datos y los servicios dependientes están **simulados (mocks)**, por lo que no se accede a Supabase ni a Firebase. El token JWT se firma realmente, de modo que `verifyToken` se ejecuta sin simulación.

**Estrategia frontend.** Cada página se renderiza completa con Testing Library; `fetch` se reemplaza por un simulador (`test/frontend/helpers/fetchMock.js`) que responde por método y URL y registra las llamadas (URL, cabecera `Authorization` y cuerpo). El encabezado de navegación y los contextos de avisos se sustituyen por dobles. Se simula el teclado y los clics del usuario (`user-event`).

## 7. Observaciones y limitaciones

1. **DEFECTO DETECTADO · fecha de fin igual a la de inicio (RF-26.5).** Si un período se abre el último día del mes con día de corte 1 (p. ej. el 30-nov-2026 o el 31-ene-2026 con corte 1), `calcularFechaFin` devuelve `fecha_fin = fecha_inicio`: la rama de recálculo vuelve a producir el mismo día. La tabla `periodos_presupuesto` tiene `CHECK (fecha_fin > fecha_inicio)`, así que el `INSERT` fallaría con error `23514` y `abrirPeriodo` responde 500 genérico (no mapea ese código). La prueba «DEFECTO · RF-26.5…» está marcada con `it.failing`: pasa mientras el defecto exista y se pondrá en rojo al corregirlo, para avisar que hay que quitar la marca.
2. **Fechas del período.** El RF-26 dice que el usuario abre el período «indicando sus fechas y el ingreso estimado»; en la implementación (backend y web) el usuario solo indica el ingreso estimado y las fechas se calculan desde el día de corte. Las pruebas verifican la implementación actual.
3. **Rechazos del backend en la web.** `abrirPeriodo` y `crearPerfil` (api.js) lanzan una excepción ante HTTP no exitoso; la pantalla muestra «Error al conectar con el servidor» en vez del motivo (409/400). En activar y eliminar sí se muestra el motivo (con `alert`). Queda fijado en pruebas «OBSERVACIÓN».
4. **Ingreso real.** Se recalcula sumando los ingresos del rango (cierre y `actualizar-ingreso`); no existe ajuste manual del ingreso real en el backend revisado.
5. **Reloj controlado.** Las pruebas de fechas congelan solo `Date` (los temporizadores siguen reales) para que el resultado no dependa del día en que se ejecutan.
6. **Pruebas con BD y red simuladas.** Se verifica la lógica del controlador, los parámetros enviados a la base de datos y el comportamiento de las pantallas, pero no se ejecutan consultas reales ni se prueba contra PostgreSQL/Supabase; restricciones como los `CHECK` o el aislamiento por usuario a nivel SQL no se validan contra la base real.
7. **Precondición «cuenta activa».** En el código revisado solo se valida el token JWT; no se comprueba que la cuenta esté activa. No hay prueba asociada (se revisará junto con RF-09).
8. **Alcance.** Se cubren backend y frontend web. La aplicación móvil no forma parte del proyecto entregado y no se probó.
