## 2. Requerimiento verificado

Texto del documento de requisitos (las precondiciones se muestran en una sola línea):

> **RF-05: Gestionar imprevistos.** El sistema deberá permitir registrar, consultar, modificar y eliminar gastos imprevistos (no planificados), clasificados por categoría. Cada imprevisto se contabiliza contra la porción de imprevistos del presupuesto del período activo. El sistema avisará cuando el consumo de esa porción se acerque al límite y, al cerrar un período con la porción casi sin usar, sugerirá redirigir ese dinero a ahorros.
>
> **Precondiciones:** El usuario ha iniciado sesión; La cuenta está activa.
>
> **Requisitos específicos:**
> - **RF-05.1:** El monto debe ser mayor que cero.
> - **RF-05.2:** Cada imprevisto se contabiliza contra la porción de imprevistos del presupuesto del período activo.
> - **RF-05.3:** Se genera una notificación al alcanzar el 85 % de consumo de esa porción.
> - **RF-05.4:** Al cerrar el período con la porción casi sin usar, se genera una notificación de sugerencia hacia ahorros.
> - **RF-05.5:** El sistema no transfiere dinero a ahorros de forma automática.
> - **RF-05.6:** Cada usuario accede solo a sus propios imprevistos.

## 3. Entorno y estrategia

| Elemento | Detalle |
|---|---|
| Pruebas de backend | Jest (`^30.5.2`) + Supertest (`^7.3.2`); configuración en `Backend/jest.config.js` y `test/backend/setupEnv.js` |
| Pruebas de frontend | Vitest (`^5.1.0`) + Testing Library (`react`, `user-event`, `jest-dom`) + jsdom; configuración en `Frontend/vite.config.js` (bloque `test`) y `Frontend/setupTests.js` |
| Comando backend | `npx jest rf05` (desde `Backend/`) |
| Comando frontend | `npx vitest run test/frontend/rf05` (desde `Frontend/`; `npm test` abre el modo observador) |

**Estrategia backend.** Se monta una aplicación Express con solo las rutas del módulo. La base de datos y los servicios dependientes están **simulados (mocks)**, por lo que no se accede a Supabase ni a Firebase. El token JWT se firma realmente, de modo que `verifyToken` se ejecuta sin simulación.

**Estrategia frontend.** Cada página se renderiza completa con Testing Library; `fetch` se reemplaza por un simulador (`test/frontend/helpers/fetchMock.js`) que responde por método y URL y registra las llamadas (URL, cabecera `Authorization` y cuerpo). El encabezado de navegación y los contextos de avisos se sustituyen por dobles. Se simula el teclado y los clics del usuario (`user-event`).

## 7. Observaciones y limitaciones

1. **Causa obligatoria solo en la web.** El formulario exige la causa; el backend solo exige el monto (los demás campos quedan en `null`). El RF-05 menciona monto y categoría, y la categoría tampoco es obligatoria en ninguna capa.
2. **Cierre de período.** La notificación de sugerencia se genera desde `cerrarPeriodo` (RF-26); aquí se prueba el servicio y en RF-26 la invocación.
3. **Alcance de las notificaciones.** Se verifica la creación del registro de notificación; el envío push (Firebase) está simulado.
4. **Pruebas con BD y red simuladas.** Se verifica la lógica del controlador, los parámetros enviados a la base de datos y el comportamiento de las pantallas, pero no se ejecutan consultas reales ni se prueba contra PostgreSQL/Supabase; restricciones como los `CHECK` o el aislamiento por usuario a nivel SQL no se validan contra la base real.
5. **Precondición «cuenta activa».** En el código revisado solo se valida el token JWT; no se comprueba que la cuenta esté activa. No hay prueba asociada (se revisará junto con RF-09).
6. **Alcance.** Se cubren backend y frontend web. La aplicación móvil no forma parte del proyecto entregado y no se probó.
7. **Requisito para ejecutar las pruebas.** Estas pruebas cargan `movimientosController.js`, que en la copia recibida exporta `getMovimientos` sin definirla (ver `README.md` de esta carpeta, hallazgo H-01). Mientras no se corrija, las pruebas de backend de este módulo no pueden cargar el controlador.
